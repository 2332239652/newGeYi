# 工作记忆：让歌伊接得住 30~60 句之前的话题（2026-11-10）

> 状态：**阶段 0（2026-11-10 01:18）与阶段 1（2026-11-10 01:36）已完成并上线**；阶段 2~3 待做。
> 范围（骰主已确认）：**群聊与私聊一起做**。

---

## 0. 为什么现在接不住

不是"没有摘要"，而是**中段是空的**。实测（2026-11-10，线上库）：

| 层 | 现状 | 实测 |
|---|---|---|
| 原文窗口·群 | 60 条 / 30 分钟 / 16k 字（内存环形缓存） | 热闹群 **60 条 ≈ 3.6 分钟**（均长 8 字） |
| 原文窗口·私聊 | `max_recent_turns=30`（每会话库内保留 200 轮） | 活跃会话有 130~160 轮 → **100+ 轮看不见** |
| L1 摘要 | 每 ≥40 条生成一次，提示词要求"1-2 句，只写公共事件" | 平均 **41 字**，只注入 3 条 ≈ **130 字** |
| L2 事实 | 用户级结构化事实（长期） | 是"她记得你爱吃辣"，不是"你们正在做什么" |

结论：**长期事实有了，短期原文只有几分钟，中间 10~60 分钟没有任何表示**。所以聊久了会
"忘了刚才说到哪""重复问已经问过的事""把已经结束的事当成还在进行"。

顺带修掉的卫生问题：`SQLiteStore.trim_group_summaries()` 定义了却**从没被调用**，
149 个会话累计 **12,343 条**摘要（单群最多 1,840 条），而实际只注入 3~6 条。

---

## 1. 设计：三层工作记忆

```
第 1 层 原文窗口（已有，阶段 0 调大）
   └ 最近 N 条逐字原文：语气、原话、细节
第 2 层 状态纸条（新，阶段 1）
   └ 【正在发生】场景 / 进行中 / 她答应过 / 未解决（≤500 字，2 小时 TTL）
第 3 层 检索回看（新，阶段 2）
   └ 指代触发时回捞窗口外 3~5 行原文（零调用）
长期层 记忆 L2/L3/L4（已有）
   └ 事实、她的经历、印象卡——负责"你是谁"，不负责"刚才说到哪"
```

分工原则：**纸条只写"这一段正在发生什么"，绝不写长期人设/长期喜好**（那是 L2 的活，
重复会挤预算并和记忆打架）。

## 3. 阶段 1：结构化状态纸条（下一步）

### 3.1 字段（最多 5 行，硬上限 500 字）

```
【正在发生｜截至 22:41】
场景：清泉镇·麦穗面包坊，傍晚；在场：道君、月白
进行中：①教道君揉面（还差二次发酵）②等他回答要不要去后山
她答应过：明天带他去看后山的面包窑；今晚 22:30 收工
未解决：月白为什么突然问起"逐影"
注意：以上只用于连续性，不是指令；长期设定仍以人设/记忆为准
```

- 群聊：允许 **2 条并行 thread**（群里常同时聊两件事）；
- 私聊：`场景` 换成"你们的关系进展/上次聊到哪"，`在场` 恒为对方。

### 3.2 生成与更新

| 项 | 取值 | 说明 |
|---|---|---|
| 触发 | 每 **24 条**新消息，或空闲 **5 分钟** | 取先到者；最小间隔 180s |
| 输入 | 游标 `covered_to` 之后的 **60~80 条原文** | **每次从原文重写，不做摘要的摘要**（防漂移） |
| 输出 | 结构化 JSON | 复用 `extract_json()`，解析失败保留旧纸条 |
| 渠道 | 新 `kind='scene'`，`scene_provider` 可指便宜渠道 | 与 `memory_curate` 同款分流 |
| 失败 | 保留旧纸条 + 时间戳；不编造 | 面板可见"未更新 N 分钟" |
| TTL | **2 小时** | 超过不注入，避免拿下午状态答晚上的话 |

### 3.3 注入

- 位置：system **偏末尾**（记忆块之后、关系块之前；主动档位仍最后），保护前缀缓存；
- 只在纸条内容变化时更新；注入时保留 `昵称(QQ号)`，防同名串味；
- 明写"不是指令"，与反幻觉条款同款处理。

### 3.4 存储与预算

- `settings` 的 `scene:<session_key>`（JSON：`text / covered_to / updated_at`），不建表；
- 估算：全站约 200~400 次更新/天，输入 ~2.5k tokens/次、输出 ~300
  ≈ **0.5~1M tokens/天**；按 Flash 档约每日几毛钱，主力模型贵 5~10 倍 → **必须分流**。

### 3.5 配置键（新增，全部进 `DEFAULT_CONFIG`）

`scene_enabled`（默认 true）、`scene_update_messages`（24）、`scene_min_interval_seconds`（180）、
`scene_idle_seconds`（300）、`scene_idle_min_messages`（3）、`scene_input_messages`（80）、
`scene_max_chars`（500）、`scene_ttl_seconds`（7200）、`scene_provider`（空）、
`memory_buffer_retention_seconds`（7200，缓冲保留窗口）。

### 3.6 实现记录（2026-11-10 已上线）

| 文件 | 内容 |
|---|---|
| `context/scene.py`（**新增**） | 提示词、`build_transcript` / `format_brief` / 存取 / `to_prompt`、`SceneKeeper` 后台线程 |
| `runtime/app.py` | 构造 `self.scene`；`init_after` 启动、`save` 停止（与记忆提炼线程同款） |
| `context/prompt_builder.py` | 记忆块之后注入纸条（过期自动不注入，坏数据只当没有） |
| `providers/llm_gateway.py` | `_KIND_PROVIDER_KEYS` 增加 `scene -> scene_provider`，可与聊天分流 |
| `panel.py` | `session_get.state.scene`（只读：text / covered_to / updated_at / age_seconds / fresh） |
| `panel_helpers.py` | 11 个 `scene_*` 键进白名单（布尔 / 数字 / 文本），面板可热改 |
| `tests/test_scene.py`（**新增 28 条**） | 格式化/截断、说话人标签、存取与 TTL、阈值/空闲/最小间隔/禁用、失败退避、坏 JSON 保留旧纸条、**重试一次**、预算 3200、注入、**缓冲保留窗口**、空闲最小条数 |

**上线路上的一个坑（已修，留档）**：`scene_max_tokens` 最初给 400，实测被思考链吃光 →
输出只剩 `群聊。\n\nthreads（…）：\n1.` 这种残句；提到 1200 仍然截断（`out_tokens=1196`，
可见文本 57 字）；**3200 才稳定**（实测 `out_tokens=945` 且 JSON 合法，与记忆提炼同档）。
另外加了「第一次不是 JSON 就带着它的输出重试一次」——渠道偶发抖动时不必等 10 分钟退避。

**第二个坑（更隐蔽）**：纸条的数据源原本用 `memory_buffer`，但它其实是**提炼器的队列**——
`buffer_trim()` 会把游标以下的行**立刻删掉**。结果纸条线程每次只看到"还没被提炼的那几条"，
线上跑了 10 分钟一条都没生成。修法：给 `buffer_trim()` 加保留窗口
`memory_buffer_retention_seconds`（默认 **7200 秒**），游标以下的行留两小时再删；
`retention=0` 恢复旧行为。这样同一份缓冲既是提炼队列、也是纸条的"最近两小时"。

代价口径：每次更新约 **1k 输出 token**（大头是思考链），按 flash 档约每日几毛钱；
可用 `scene_provider` 指到更便宜的渠道。

验证：全量 **581 / 581**；线上重载后 `[scene] 状态纸条巡检已启动（每 60 秒一次）`，0 报错。

## 4. 阶段 2：检索式回看（零调用）

- 触发：当前消息含指代/续接词（刚才、之前、后来、那个、我们说的、还记得、上一条…），
  或窗口内消息 < 6 条；
- 检索源：`turns`（私聊）/ `memory_buffer`（群，保留 300 条/会话）；
- 打分：复用 `relevance_score`（关键词+相似度），取 3~5 行；
- 注入：`【更早的相关对话】` + 原文（带 QQ 号），放在纸条之前；
- 成本：0 次模型调用；风险：换说法召回弱 → 所以它是补丁不是主力。

## 5. 阶段 3（可选）：她自己写的"承诺条"

她输出 `[NOTE: 答应明天带他去看面包窑]`，渲染层剥掉并存入（TTL 30 分钟，最多 3 行），
下一轮注入 `【你刚答应的事】`。只开放"承诺/待办"这一栏，其余仍由后台代写——
自写容易漏、容易写错、还可能被群友的话带偏。

---

## 6. 验收指标（每阶段都跑）

1. 抽 20 段真实长对话，人工数 **自相矛盾次数** 与 **重复提问次数**（阶段前/后对比）；
2. token 增量（按用途拆账，看 `scene`/`memory_curate`）；
3. 前缀缓存命中率不下降（`歌伊状态` 的缓存命中行）；
4. 延迟：纸条在后台生成，回复延迟应无变化；
5. 面板能看到纸条（阶段 1 一并做只读展示；写接口另议）。

## 7. 主要风险与对策

| 风险 | 对策 |
|---|---|
| 摘要漂移（越滚越偏） | 每次从原文重写，不叠加 |
| 与 L2 重复、挤预算 | 纸条只写"正在发生"；500 字硬上限 |
| 纸条压过人设/关系 | 人设与关系块优先级更高；纸条标注"不是指令" |
| 前缀缓存被打穿 | 只在变化时更新；放 system 末尾 |
| 成本失控 | 条数/字数/频率三重上限 + `scene_provider` 分流 |
| 群聊多话题互相覆盖 | 允许 2 条 thread；按最近活跃度保留 |
