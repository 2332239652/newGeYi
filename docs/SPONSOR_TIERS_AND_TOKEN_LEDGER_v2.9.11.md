# v2.9.11：赞助两档 + token 总账

2026-11-08。两件独立的事一起发：爱发电分两档（6 元 / 20 元），以及「歌伊状态」里能一眼看到今天总共烧了多少 token。

---

## 一、赞助两档

### 档位与权益

档位是**累计**的，二档包含一档的全部。判定逻辑只有一处：`runtime/sponsors.py`。

| 权益 | 一档「请歌伊吃一天饭」6 元 | 二档「帮歌伊租半个月房子」20 元 |
|---|---|---|
| 私聊每日额度 | 60 → **100** | 60 → **120** |
| 拥挤期收紧（会压到 35） | **不收紧** | **不收紧** |
| 记忆不裁剪 | — | ✅ |
| 记忆召回下限 | — | **8 条**（原来陌生阶段只给 2 条） |
| 内测优先 | — | ✅ |
| 鸣谢（歌伊菜单 / 爱发电页面） | ✅ | ✅ |

### 配置键

```jsonc
"sponsor_tier1_ids": [],                    // 一档名单（QQ 号字符串）
"sponsor_tier2_ids": [],                    // 二档名单
"private_daily_quota_sponsor_tier1": 100,
"private_daily_quota_sponsor_tier2": 120,
"sponsor_memory_keep": true,                // 二档记忆免裁剪总开关
"sponsor_fact_floor": 8,                    // 二档记忆召回下限，0 = 不设
"beta_ids": [],                             // 额外内测名单（二档自动在内）

"sponsor_ids": [],                          // 旧键：按一档算，无需迁移
"private_daily_quota_sponsor": 0            // 旧键：两档额度都读不到时的回落值
```

**升级不需要迁移。** 2.9.10 里只写了 `sponsor_ids` + `private_daily_quota_sponsor` 的配置，
升级后仍然算一档、仍然用旧额度（有测试锁着这一条）。默认三份名单都是空，功能默认全关。

### 命令

```
赞助名单                  看两档成员、额度、内测名单
赞助加 <QQ> [1/2]         加人（不写档位按一档）
赞助删 <QQ>               从所有名单里移除
```

`赞助加` 会把这个人从另一档里摘掉——档位是累计的，同时出现在两档只会让"降档后旧权益还在"。

> 爱发电那边确认收到钱再加人。人工白名单是**故意**的：爱发电对小项目没有稳定回调，
> 而且「付钱→额度立刻到账」会把赞助变成交易。

### 为什么记忆不裁剪要改两处

`trim_user_facts` 有两条裁剪路径：按单人裁剪、按群总量裁剪。只跳过前者是不够的——
按群总量那次照样会把赞助者当「低分条目」挤掉，「记忆不裁剪」就只是半句话。

实现上不能简单把受保护行当成「手工事实」：手工事实在「手工本身就超了」那条分支里
依然会按分数砍到 limit 以内（线上真有人手工记了 60 条）。所以受保护行是
**整个移出裁剪候选集**——不参与淘汰，也不占名额（`protect_ids`）。

### 明确没做的四件事

1. **不卖好感度**（不加速、不免扣分、不提升上限）。这条线一破，整套关系系统的可信度就没了。
2. **不卖定制台词/剧情**。那是劳动，不可扩展，而且最像「付费内容」。
3. **不卖立绘/皮肤/隐藏功能解锁**。内容解锁＝商品化。
4. **不做赞助者 QQ 群**。在 QQ 上组织付费用户是整套方案里唯一真正危险的动作。

## 二、token 总账

### 先说结论：记账本来就是全的

`api_calls` 表一直在记 `in_tokens / out_tokens / cached_tokens / kind / model / session_key / ok`，
网关的每一次尝试（成功、空回复、超时、4xx/5xx）都过 `_record()`。实测今天 125 次调用：

| kind | 次数 | 输入 | 输出 | 是什么 |
|---|---|---|---|---|
| `active` | 62 | 403,932 | 13,540 | 主动搭话（含搭话判断，判断是本地算分不花 token） |
| `passive` | 25 | 210,083 | 12,038 | 群聊/私聊被动回复 |
| `memory_curate` | 36 | 86,935 | 23,847 | 记忆提炼 |
| `affection` | 2 | 3,067 | 1,176 | 好感评审 |

成功调用里 **0 行**缺 usage（`in_tokens=0`），说明上游透传没丢。12 次失败全是
`memory_curate / empty_content`（思考链吃光 max_tokens），失败本来就没有 usage。

### 发现并修掉的两个口径问题

1. **按用途拆账只统计输入。** 而记忆提炼恰恰是输入巨大、输出很小的一类
   （一轮几十条消息压进去，只吐一小段 JSON）。只看输入会把提炼算成头号开销，
   看合计才对得上账单。→ `today_stats_by_kind()` 补上 `out_tokens` / `total_tokens`，
   排序改按合计。
2. **`kind` 分不出群聊和私聊。** `passive` 既是群里接一句话，也是私聊聊半小时。
   → 新增 `today_stats_by_scope()`，按会话键拆成 群聊 / 私聊 / 其它（好感评审不属于任何会话）。

### 两个已知盲点（改不了，只能知道）

- **TTS 不在这个账里。** 语音合成按字符计费，走 `voice/client.py` 另一条链路，跟 token 无关。
- **缓存命中率 0% 可能是渠道口径。** 今天 709k 输入、0 命中，是因为当前渠道
  `gemini-3.8-flash-tiered` 不透传 `prompt_tokens_details`。11-06/11-07 有命中
  （61 万 / 20 万），那两天跑的是别的渠道。看到 0% 先怀疑渠道，别怀疑插件。

### 顺带：月度账本

新增 `range_stats(days)`，一次 SQL 出最近 N 天的调用数、输入、输出、合计、缓存命中。
发爱发电月度收支时直接用这个数，不用手工翻。
