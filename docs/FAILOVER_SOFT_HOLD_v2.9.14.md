# v2.9.14：全挂「软降级」+ 探测对链路抖动更宽容（2026-11-12）

## 一、问题与现场证据

骰主的反馈：「渠道流转动不动就报渠道全挂，我的渠道大多是中转站或者反代，波动很正常。」

从生产库 `settings` 的 `gw.history` 能看到当天真实轨迹（00:09~00:33）：

```
00:09:10  star-low  → ginka-low    all_down timeout
00:10:29  ginka-low → local-proxy  manual 锚点      ← 人工切回
00:12:07  local-proxy → ginka-low  all_down timeout
00:21:52  ginka-low → local-proxy  manual 锚点      ← 又一次人工切回
00:33:06  local-proxy → star-tiered auto http_502 x2
```

两次 `all_down` 都发生在**十几秒内的一串超时**上，随后都靠人工切回。也就是说：
老逻辑把「一次抖动」直接当成「全线瘫痪」，通知发出去、兜底锁上，等人来救。

**探测程序本身是正常的**：11-11 的日志里有三次真实恢复记录——
`13:03:33`、`15:53:38`、`22:49:20` 都是 `probe_recover`（ginka-low → star-tiered）。
所以这次不是修探测的「有没有跑」，而是让它在抖动面前别那么容易被判死。

## 二、改动 1：全挂不再立刻锁定

```
一次 chat() 两轮全挂
   │
   ├─ retry_before_hold_seconds = 0 ? ──→ 老行为：通知 + 锁兜底（保留给应急配置）
   │
   └─ 默认 300 秒
        ├─ 记 pending_hold_at = now + 300，**不通知、不锁定**
        ├─ 当前渠道临时切到兜底（official-chat），保证这几分钟还有话可回
        ├─ 期间任何一次真实调用成功 → 撤销 pending，当没发生过
        ├─ 探测线程到点（`retry_pending_once`，锚点优先、不越过锚点）
        │     ├─ 有一个通了 → 切回去，**不通知骰主**
        │     └─ 全都还不通 → 才走 `_escalate_to_last_resort`：通知 + 锁定
        └─ 冷却期内的再次全挂**不重置倒计时**（否则晚上一直有人聊，永远到不了点）
```

要点：

- 「锚点」语义不变：重试只从锚点及其以下开始，绝不自己爬回更贵的上游；
- 手动操作（`切换渠道 X` / `切换渠道 自动`）会撤销待重试，骰主永远优先；
- 状态命令里会多一行 `⏳ 全挂冷却中：N 秒后从锚点重试`；
- 通知仍然受 `notify_cooldown_seconds` 节流，且**只在重试失败时**发一次。

## 三、改动 2：链路抖动的容忍度

| 项 | 以前 | 现在 | 为什么 |
|---|---|---|---|
| 真实调用超时/连不上 | 立刻计入失败次数（`fail_threshold=2` 就判死） | 若该渠道 **90 秒内刚成功过**，这次只记 INFO、不计数（`failure_grace_seconds`） | 夜里偶发 reset / 40~70s 慢响应，不该把整条线判死 5 分钟 |
| 探测判定「活着」 | 只认 HTTP 200 | 200 与 **429** 都算（`probe_ok_statuses`） | 被限流说明路是通的，只是忙；真死交给真实调用累计 |
| 探测遇到连接抖动 | 一次异常就判「未恢复」 | 先重试 1 次（`probe_retry`） | 单次 reset 多半是瞬时抖动 |
| 全挂后的处置 | 立即锁定 | 5 分钟后从锚点重试，成功即恢复 | 见上 |

**探测的可观测性**（本轮顺手补的）：以前探测线程起来后一行日志都没有，出了问题
没法判断「它到底在跑吗」。现在启动时打一行
`渠道探测已启动：每 300 秒一轮，单次超时 10 秒，失败重试 1 次，刚成功过 90 秒内的抖动不计故障`，
某一轮真的探测失败时打 `探测未通过：xxx（下一轮再试；429 视为活着）`。

## 四、配置

```jsonc
"failover": {
  "retry_before_hold_seconds": 300,   // 0 = 退回「立刻锁定」
  "failure_grace_seconds": 90,        // 刚成功过的渠道，这次抖动不计故障
  "probe_ok_statuses": [200, 429],    // 探测认为"活着"的状态码
  "probe_retry": 1                    // 探测遇到连接异常先重试几次
}
```

## 五、验证

- 新增 11 条测试（`tests/test_gateway_failover.py` 的 `SoftHoldTest` / `ToleranceTest`）：
  第一次全挂不锁不通知、兜底切换后其它渠道仍在候选、重试成功静默恢复、重试失败才锁+通知、
  冷却期成功撤销 pending、重复全挂不重置倒计时、手动切换撤销 pending、状态文本显示冷却；
  探测把 429 当活着、连接抖动重试一次、刚成功过的超时不计故障。
- 老语义（立刻锁定）仍有 14 条用例守着，靠 `retry_before_hold_seconds=0` 显式开启。
- 全量 **647 / 647** 通过。

## 六、回滚

`failover.retry_before_hold_seconds` 改成 `0` 即恢复 2026-11-01 的「立刻锁定 + 通知」；
代码侧直接 `git revert` 本版即可，数据没有迁移。
