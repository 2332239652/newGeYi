# 私聊额度的重新分配（v2.9.7）

> 注：下文里的 `用户A`～`用户G` 是真实 QQ 号的替代，原始账号已隐去。

## 问题

11-06 全局限额 300 被打满。打满之后**所有人**都排不上——包括刚来的、只说了两句话的人。

## 先把分布拉出来（11-06，12 个私聊对象，317 条回复）

```
 1. 用户A   87 条   累计  87 = 27.4%
 2. 用户B   73 条   累计 160 = 50.5%   ← 两个人吃掉一半
 3. 用户C   34 条   累计 194 = 61.2%
 4. 用户D   24 条   累计 218 = 68.8%
 5. 用户E   20 条   累计 238 = 75.1%
 6. 用户F   16 条   累计 254 = 80.1%
 …
12. 用户G    1 条   累计 317 = 100%

中位数 16 | 均值 26.4 | 最高 87 = 中位数的 5.6 倍
```

**结论：不是总量不够，是分配太不均。** 单纯把 300 抬到 500，只会让这两名吃到 150，
尾部用户的处境一点没变，成本却翻倍。

而且话痨的收益本来就在衰减：用户A 那 58 条评审只落 **1 分**
（同一标签每天只记 2 次，其余全是 neutral）——砍他的额度，对关系系统几乎没有影响。

## 改法：三段

| 旋钮 | 旧 | 新 | 作用 |
|---|---|---|---|
| `private_daily_quota` | 100 | **60** | 削头部。第 3 名才 34 条，60 已经覆盖 99% 的人 |
| `private_daily_quota_global` | 300 | **400** | 给更多人留位置（14 人 × 28 条 ≈ 392） |
| `private_quota_squeeze_at` | — | **0.7** | 全局用到 70%（280 条）开始收紧 |
| `private_quota_squeeze` | — | **35** | 收紧后单人上限压到 35，保证晚来的人还有得聊 |

「拥挤收紧」平时完全不生效，只在真的挤的时候启动。逻辑在
`runtime/private_gate.py::squeezed()` / `_effective_user_quota()`，
`allow()` 和 `usage_text()` 共用同一个计算，不会出现两套口径。

## 回放 11-06

```
用户A   87 → 60（-27）
用户B   73 → 60（-13）
用户C   34 → 34
用户D   24 → 24
其余 8 人     不变
合计        317 → 277（用到全局限额的 69%，没触发收紧）
```

**尾部用户一条都没被影响**，只有两名话痨各少聊二十来分钟。

## 现在怎么看

骰主发 `私聊用量`：

```
本会话今日私聊回复 34 条（限额 60）
全体私聊今日 277 条（限额 400，已用 69%）
```

挤的时候会多一段：

```
全体私聊今日 285 条（限额 400，已用 71%）⚠ 拥挤期：单人上限已压到 35
```

调试台 →「私聊并发保护」组能看到全部四个数，保存即热更新。

## 顺带修的：测试临时目录泄漏

`%TEMP%` 里堆了 **9961 个 `geyi_*` 目录、1.7 GB**，C 盘只剩 3.3 GB 之后
sqlite 开始报 `disk I/O error` / `unable to open database file`，
表现为「测试莫名其妙红了」，报错点还全在 storage 层——看着像代码坏了，其实是盘满了。

`tests/__init__.py` 现在在退出时清掉**本次新增**的目录（只删新增的，
不碰别人留下的；要留现场排查就 `GEYI_KEEP_TEST_DATA=1`）。
实测每轮残留从 +20~50 降到 +1（剩下的是被 sqlite 文件句柄占住的，Windows 删不掉）。

## 回滚

| 改动 | 回滚 |
|---|---|
| 额度 | 调试台改回 100 / 300，或 `config.json.bak-quota-20261107` |
| 拥挤收紧 | `private_quota_squeeze_at: 0`（等于关掉） |
| 测试清理 | 删 `tests/__init__.py` 里的 atexit 段 |
